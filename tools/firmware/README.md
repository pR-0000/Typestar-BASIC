# Firmware construction

HD6301 sources are in `../../src/`. The published firmware is **0.4.93-dev**, validated on S-70 and the documented S-60 revision. Its incremental pipeline extends .88 (`build_llist.py`) with .89's glyph-mask relocation fix, .91's separate paper-correction step, .92's reduced 1/4 gain and .93's continuous repeated glyphs and lossless font repacking. Ready-to-program images and resource statistics are in [firmware/0.4.93-dev](../../firmware/0.4.93-dev/README.md).

These scripts form an **incremental build pipeline**. Each stage checks the previous CPU image and symbol map before modifying the relevant ROM regions. `build.py` is the initial stage, rather than an independent build of the latest version. Intermediate images, manifests and reports live in the ignored `build/` directory.

Run scripts from the repository root. The existing pipeline requires the A09 assembler, the original Canon firmware and locally generated intermediate reports. It retains paths to the adjacent ROMReader research workspace. A standalone, configurable build remains a separate publication task. This reorganization changes no firmware bytes.

Some shared modules retain a `validate_` prefix because assembly helpers were developed alongside verification code; they remain here when construction stages import them. Independent diagnostics and hardware probes are stored in the ignored `_local/development/` tree.

Archived intermediate releases may be supplied with `TYPESTAR_FIRMWARE_ARCHIVE` or the ignored `_local/build-inputs.ini` (`[inputs]`, `firmware_archive = /path/to/archive`). Output always remains in the project's generated `release/` folder.

For .89, `build_glyph_mask.py` verifies the .88 image and the final row-mask table before changing its single immediate reference and version banner. `prepare_glyph_mask.py` requires a passing actual-ROM regression report for that exact candidate hash. It generates a 32 KiB IC8 image and a 64 KiB mirrored image; the .88 files remain available. Sparse sprites and one-hot rows are required checks: an all-black glyph alone can hide an incorrect mask table.

For .91, `src/paper-y-poststep.asm` hooks the successful PMMOVE commit (`FEED`, `MOVE`, `LLOCATE`). An accumulator at `$1B8D` distributes three separate one-unit forward corrections across eight reversals of at least two units. The complete native reverse approach is preserved. An extra movement re-enters the existing paper-call preparation; a completed nominal Y prevents recursive compensation. Single-unit reversals, forward travel, `ORIGIN` and `LSPACING` preserve the fraction; boot clears it. Font records and keyword spellings are repacked, sharing eight exact font-stream bytes without changing any decoded glyph. All 37 token pointers, 54 command entries, direct spelling references and the LIST suffix alias are updated and checked. Net cost from .89: 32 ROM bytes and one working-RAM byte; 70 explicit ROM bytes remain, with 5,951 empty BASIC bytes unchanged. Native motor-call and coil-state comparisons against the BASIC prototype gate packaging, together with all 95 decoded characters and X/Y checks. Mechanical slip, skew and timing still require a hardware test.

The unsuccessful .90 reverse-overshoot experiment is archived outside the public sources. It is not a prerequisite of .91, which retains .89's preparer and follows the separate-step BASIC prototype.

For .92, the shared assembly parameter `YPGAIN` is 64/256; .91 remains reproducible with 96/256. Reassembly verifies a single changed gain operand, plus one banner digit. All motor control flow, X commands, font/dictionary locations and memory allocations remain byte-identical to .91. Checks cover 3,840 fraction/distance combinations, three full accumulator cycles, and an actual four-round-trip interpreter run with exactly one extra forward call and zero commanded X drift. The same `XY CHECK` diagnostic is used on hardware without any BASIC-side compensation. Hardware trials on S-60/S-70 selected this smaller gain; the remaining mechanical error depends on paper transport and paper condition.

For **.93**, `build_glyph_repeat.py` starts from the verified .92 image. `src/paper-glyph-repeat.asm` adds `GLYPH A(first),width,height[,mode[,repeat]]` (also matrix sources), repeat 1..16 and mode 4 for large square pixels. One rendered band is reused for all copies; a 16×16 mode-4 motif needs 348 temporary bytes whether repeated once or ten times. Ten walls use two native horizontal sweeps. BREAK is polled between native blocks; empty bands are skipped. The .92 motor routines, serial core and Y gain are retained.

Space comes from lossless font run selection (`src/paper-font-runs-byte.asm`) and exact keyword sharing. All 95 decoded characters, 37 token entries and 54 command links are checked. The 32 KiB ROM has 61 explicitly free bytes; empty BASIC RAM remains 5,951 bytes. `prepare_glyph_repeat.py` gates 32 KiB socket and 64 KiB mirrored images on the exact candidate's native glyph/font/BREAK regression report. Studio includes the matching symbols and mode-4 glyph editing/import. The user has confirmed the continuous rows and updated games on hardware. Native checks additionally cover raster contents, buffer lifetime, BREAK and far-column registration; no quantified printing-speed claim is made.
